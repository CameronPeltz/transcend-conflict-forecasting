Predicting conflict from transcribed signals: a graph-based methodology

A working reference covering the extraction-to-graph pipeline, the public datasets available for backtesting, and a battery of models to test against them in sequence — starting with the graph-native model described in the methodology.

Pipeline

Collecting signal events into a graph database

Four stages sit between raw audio and a queryable graph. Each stage introduces a specific failure mode worth designing around from the start.

  • 1

    Transcription and normalization

    ASR on radio and audio feeds, with speaker diarization, language ID, and dialect handling for multilingual regional sources. Every utterance keeps a confidence score. Low-confidence spans carry that uncertainty downstream instead of being silently treated as ground truth.

  • 2

    Event extraction

    Extraction runs against a controlled event schema, not open-ended relation extraction. CAMEO or ACLED-style coding (actor, action, target, location, time, source) gives a validated vocabulary already accepted in conflict research. An LLM or fine-tuned classifier outputs coded tuples from transcript spans, with a secondary classifier for escalation severity.

  • 3

    Entity resolution

    Actors get named inconsistently across sources, languages, and transliterations. Build a canonical entity table with aliases and resolve mentions against it before graph write — resolution errors compound into phantom nodes if deferred.

  • 4

    Staged, idempotent graph write

    Land raw tuples in a staging table, run entity resolution and near-duplicate collapsing (one broadcast event reported by three stations shouldn't become three graph events), then batch-write with upserts keyed on (actor, action, location, time-bucket).

Schema

Graph node and edge design

Node types

ActorMilitia, official, ethnic or political group. Canonical entity, aliases attached.
LocationGeo hierarchy — village → district → region — for aggregation at any level.
EventA coded occurrence: actor, action, severity, timestamp.
SourceRadio station, frequency, or broadcast outlet, with a reliability tier.
Claim / StatementRhetoric tracked separately from physical events — propaganda and real reporting shouldn't share a node type.

Edge types

PARTICIPATED_INActor → Event
OCCURRED_ATEvent → Location
REPORTED_BYEvent → Source, carries provenance
PRECEDED_BY / ESCALATED_FROMEvent → Event, builds escalation chains
ALLIED_WITH / HOSTILE_TOActor → Actor, time-scoped — alliances shift, so this edge always carries a validity window
Temporal modeling is the load-bearing design choice. Use bitemporal properties — event time versus ingestion time — on every edge. Without this, a backtest can't reconstruct what the graph actually looked like at the moment a prediction would have been made, and results become hindsight-contaminated. Provenance edges back to the specific transcript span, timestamp, and source reliability tier are non-negotiable given how much propaganda mixes with real reporting in radio intelligence.
Inference

Predicting conflict from NLP inference

Two complementary families. The strongest systems run both — quantitative features drive a base-rate model, an LLM layer flags anomalies and supplies an auditable narrative.

A. Signal-based / feature engineering

Extract time-series features from the graph: event frequency by region, escalation-verb ratios using CAMEO's quad-class coding (verbal cooperation → material cooperation → verbal conflict → material conflict), rhetoric hostility trends from Source nodes, and network centrality shifts — an actor suddenly gaining alliance edges is itself a leading signal. Feed these into gradient boosting for a tabular baseline, or a temporal graph neural network (TGN, EvolveGCN) if the graph structure itself should inform the prediction rather than being flattened to features.

B. LLM-based inference

Run the model directly on aggregated recent events plus historical-analog retrieval — "this pattern resembles pre-escalation signatures from case X" — to produce a probabilistic assessment with a reasoning trace. Weaker for calibrated probability, stronger for qualitative context an event coder would miss, such as a rhetorical shift in a broadcast's tone.

Validation

Backtesting methodology

  • Strict temporal cutoffs. No feature in a training window may derive from data with an ingestion timestamp after the prediction point — this is exactly why bitemporal graph modeling matters upstream.
  • Rolling-origin splits, not random splits. Conflict events cluster geographically and temporally, so k-fold cross-validation leaks information. Train through month T, predict T+1, roll forward.
  • Beat the base rate. Compare against a naive persistence baseline ("conflict continues where it's already happening") and a historical base-rate model. A lot of published results look strong only until compared against these.
  • Brier score and precision-recall over ROC-AUC. Class imbalance makes AUC misleadingly optimistic for rare, clustered events. Stratify by lead time — a model useful at seven days may fail badly at thirty.
  • External validation set. Backtest against a documented ground truth (ACLED or UCDP onset dates) that is separate from whatever corpus built the graph, so the test isn't just validating the extraction pipeline's own biases.
Leakage risk worth documenting explicitly: if the signal-extraction model was trained or tuned with any indirect knowledge of later events — through corpus construction choices, for instance — that is a subtle vector reviewers may probe. State the extraction model's training cutoff relative to the earliest backtest window directly in the methodology writeup.
Overview

Where to get real conflict data, for free

None of these give you a raw radio-transcript layer — they're all pre-coded events or aggregated indicators. Their value is as backtesting ground truth and as prototyping data for the graph-modeling and prediction stages, before the extraction pipeline is built. Kaggle mirrors of these exist but are frequently stale or partially synthetic — the primary sources below are more reliable for anything you'll cite in a methodology document.

GDELT — Global Database of Events, Language, and Tone

Automated, CAMEO-coded, continuously updated
Free, no registrationCSV / BigQuery
AccessDirect CSV download at data.gdeltproject.org/events, or query the full history through Google BigQuery public datasets (free tier covers most exploratory work). Documentation and codebooks at gdeltproject.org/data.html.
Coverage1979–present (GDELT 1.0 backfile) and Feb 2015–present at 15-minute update cadence in GDELT 2.0, across 65 live-translated languages.
SizeThe 1979–2013 backfile alone is roughly 1.1 GB compressed. Daily export files run 6–8 MB compressed each; full 2.0-era history totals in the hundreds of GB uncompressed, over 100 million distinct coded events.
Columns58 fields per record in the 2.0 event table: dyadic actor codes (country, ethnic, religious, type classifications for both Actor1 and Actor2), CAMEO action code and its full hierarchy, Goldstein cooperation/conflict scale score, geo-referencing (lat/long, ADM1 code, feature ID) for both actors and the event location, source URL, and a date/time stamp. A companion Mentions table tracks how a story propagates across outlets.
Typical useVolume-based early warning (event-count anomaly detection), media-attention bias studies, and as the automated counterpart to ACLED's hand-coded events in comparative conflict-data reviews.
AdvantagesLargest event count of any public conflict dataset by a wide margin, real-time update cadence, genuinely global and multilingual sourcing. The tradeoff is automated coding — noisier and more duplicate-prone than hand-curated alternatives, so pair it with a dedup pass before use as ground truth.

ACLED — Armed Conflict Location and Event Data

Human-curated, subject-matter-expert coded
Free for academic / nonprofit useCSV / API
AccessRegister at acleddata.com/data-export-tool. Academic, student, and nonprofit accounts get full free access; commercial use requires a license. API access documented at acleddata.com/knowledge-base.
CoverageFull global coverage from 1997–present, updated in real time. Originally Africa-focused, expanded to global scope over the 2010s–2020s.
SizeFull global export runs to several hundred MB as CSV — well over a million individual events, and growing at roughly tens of thousands of new rows a month.
ColumnsEvent ID and date, disorder and event type (battles, violence against civilians, explosions/remote violence, riots, protests, strategic developments), primary and associate actors on both sides, named organizations involved, precise location down to admin level and coordinates, fatality count, and a source citation field for the underlying report.
Typical useThe standard ground truth in the academic conflict-forecasting literature — used as the outcome variable that GDELT-based and NLP-based prediction models are evaluated against. ACLED's own Conflict Alert System (CAST) is a production forecasting tool built on this same data.
AdvantagesHand-coded by regional analysts rather than automated extraction, giving much higher precision per event than GDELT at the cost of lower volume and slower update latency. Fatality counts and named-actor detail are more reliable than in automated datasets. Known limitation: under-coding in areas with limited media access, which is worth stating explicitly if radio-signal collection is pitched as filling that specific gap.

UCDP GED — Uppsala Conflict Data Program, Georeferenced Event Dataset

Academic gold-standard, narrowly scoped to organized violence
Free, no registrationCSV / shapefile / API
AccessDirect download at ucdp.uu.se/downloads, GED-specific page at ucdp.uu.se/downloads/index.html#ged_global. A REST API is documented in the codebook for programmatic pulls.
Coverage1989–present, annual releases plus a more frequently updated candidate/preliminary version for the current year.
SizeTens of MB as CSV — roughly 300,000 events in the full historical file, far smaller than GDELT or ACLED by design, since UCDP's inclusion bar (organized violence causing at least one fatality) is stricter.
ColumnsEvent ID, conflict/dyad ID linking to UCDP's broader conflict typology, date precision fields, side A and side B actor names with their own ID system, event type (state-based, non-state, one-sided violence), best/low/high fatality estimates, and point or centroid geocoding with a precision flag.
Typical useThe reference dataset in peace-and-conflict academic research specifically (as distinct from applied/policy forecasting, where ACLED dominates). Frequently used as a cross-check against ACLED, since the two datasets use different inclusion criteria and disagree on a meaningful share of cases.
AdvantagesHighest per-event coding rigor of the major datasets, with documented fatality estimate ranges rather than single point figures — useful for uncertainty-aware backtesting. Smaller volume is a real tradeoff for training data-hungry models, but it's the strongest available secondary ground truth to validate ACLED- or GDELT-derived predictions against.

ICEWS — Integrated Crisis Early Warning System coded event data

DARPA-lineage, automated CAMEO coding
Free, no registrationTSV via Dataverse
AccessHarvard Dataverse: dataverse.harvard.edu/dataset.xhtml?persistentId=doi:10.7910/DVN/28075. Files are organized by year, downloadable individually or in bulk through the Dataverse API.
Coverage1995–present, updated weekly, global scope.
SizeIndividual yearly files range from tens to low hundreds of MB as tab-delimited text; full history is in the low single-digit GB range uncompressed.
ColumnsEvent ID, date, source and target actor names with sector/agent codes, CAMEO event code and quad-class category, Goldstein score, and geolocation fields (country, latitude/longitude where resolvable) similar in structure to GDELT since both descend from the same CAMEO/TABARI lineage.
Typical useOriginally built for DARPA's Integrated Conflict Early Warning System program — directly relevant lineage to cite in a DARPA-facing methodology document. Widely used in political science forecasting competitions for state-level instability prediction.
AdvantagesThe most directly comparable prior-art dataset for a DARPA conflict-forecasting proposal, since it shares the program's original mandate. Automated coding like GDELT, so similar noise tradeoffs, but a cleaner actor-sector taxonomy that maps well onto a graph schema's Actor node types.

Design

A swappable battery of conflict prediction models

Each model below implements one shared interface — fit on a training window, predict a probability for the next window, expose feature importances or attention weights where applicable — so the harness can run them back-to-back against identical rolling-origin splits and compare directly. The first model is the graph-native approach from the methodology tab; everything after it is a progressively simpler or differently-shaped baseline to test it against.

  • 01

    Temporal graph neural network on the event graph

    TGN / EvolveGCN over the schema in tab 01

    Operates directly on the Actor / Location / Event / Source graph with bitemporal edges. Learns representations that update as new events and alliance shifts arrive, rather than flattening the graph to a tabular snapshot. This is the model the whole pipeline is built to feed, and the one every other entry in this list needs to beat to justify the graph infrastructure's cost.

    Why first: it's the only model that actually uses the relational structure — network centrality shifts and alliance-edge changes are legible to it in a way no tabular model can see directly.

  • 02

    Gradient-boosted trees on hand-engineered graph features

    XGBoost / LightGBM, tabular

    Flattens the graph into features per region-month: event frequency, escalation-verb ratios by CAMEO quad-class, actor-centrality deltas, source-hostility trend. Strong, fast, interpretable baseline via SHAP values.

    Why: if this matches the TGN's accuracy, the graph structure isn't earning its complexity — a genuinely useful negative result for the methodology writeup.

  • 03

    LLM-based inference with historical-analog retrieval

    Retrieval-augmented probabilistic assessment

    Feeds recent aggregated events plus retrieved historical analogs to an LLM, prompted to output a calibrated probability and reasoning trace. Weak on calibration alone; test it primarily on the qualitative flags it raises that the quantitative models miss.

    Why: captures rhetorical and contextual signal — tone shifts in broadcast sources — that event-coded models structurally can't see.

  • 04

    Autoencoder-based anomaly detection

    Unsupervised, on event-frequency time series

    Trains on "normal" event patterns per region and flags reconstruction-error spikes as candidate escalation signals, rather than predicting a labeled outcome directly. Published early-warning work using this approach on combined ACLED/GDELT data has reported strong AUC in case studies.

    Why: doesn't need labeled onset events to train, useful where ground-truth escalation labels are sparse for a given region.

  • 05

    Logistic regression on lagged event counts

    The minimum viable baseline

    Region-month event counts and their lags as the only features, no graph, no NLP. Trivial to implement and to explain to a non-technical reviewer.

    Why: every other model in this list must beat this or the added complexity has no case.

  • 06

    Naive persistence and historical base-rate

    Not a model — the floor every model is measured against

    "Conflict continues where it's already happening" and "predict the historical regional average" respectively. Neither uses features. Run both automatically as part of every harness pass, not as a one-time check.

    Why: the backtesting methodology in tab 01 depends on this comparison existing for every fold, not just once at the start.

Harness

Shared evaluation interface

Each model implements fit(train_window) and predict_proba(next_window). The harness owns the rolling-origin split, the metric computation, and the leaderboard — models never see data outside their assigned window.

# pseudocode — rolling-origin battery runner models = [ "tgn_graph", "gbm_graph_features", "llm_retrieval", "autoencoder_anomaly", "logreg_lagged_counts", "naive_persistence", "historical_base_rate" ] for fold in rolling_origin_splits(start="2010-01", step="1M", horizon="1M"): train, test = fold.train_window, fold.test_window for name in models: model = load(name) model.fit(train) # no leakage past train cutoff probs = model.predict_proba(test) log_metrics(name, fold, brier(probs, test.labels), precision_recall(probs, test.labels), lead_time=fold.horizon) leaderboard = aggregate(log, group_by=["model", "lead_time", "region"])
Scoring

Metrics tracked per model, per fold

Brier score
Calibration quality — how close predicted probabilities land to actual outcomes.
Precision / recall
Preferred over ROC-AUC given how rare and clustered conflict events are.
Lead-time stratification
Same metrics recomputed at 7-, 14-, and 30-day horizons — accuracy typically degrades unevenly across models.
Delta vs. base rate
Every model's score reported alongside the naive persistence and historical base-rate floor from the same fold.
External validation gap
Performance on the primary training ground truth (e.g. GDELT) versus an independent dataset (e.g. UCDP) — a large gap signals overfitting to one source's coding biases.
Run order matters less than fold discipline. The battery can execute in any sequence, but every model in every fold must respect the same temporal cutoff from the methodology tab — no feature computed with an ingestion timestamp after the fold's prediction point, for any model including the LLM-retrieval one, where this is easiest to violate accidentally through a retrieval index built on the full corpus.
