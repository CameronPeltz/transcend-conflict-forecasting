157 real iterations to improve geo-located event prediction: the best results found across this entire project

Not the country-week escalation question — the actual DARPA-specified unit: will a real event occur in this specific ~55km grid cell within 10 or 14 days. Three search phases, each backtested under rolling-origin, never-look-ahead validation: a 125-configuration feature/model sweep, full rigorous validation of the most promising candidates, and a hyperparameter refinement pass that found new, genuine best results.

Base

The task and its ground truth

Real UCDP GED v26.1 events, assigned to real PRIO-GRID cells (~55km, verified 99.99% match to UCDP's own field), 19 countries across DARPA's three named regions. 228,851 (cell, weekly issue date) rows, 464 active cells, forecasting whether at least one event occurs within 10 or 14 days.

The mega feature set

Every data source integrated across rounds 1-5, combined

This search draws on one merged dataset (discrete_event_candidates_mega.csv, 60 columns) combining every real, verified feature family built so far:

UCDP-derived event historyCore

Cumulative counts (30/60/90/365-day windows), days-since-last-event, momentum deltas, immediate (ring-1) and wider (ring-2) spatial neighbor counts, Hawkes-kernel exponential-decay intensity (self and neighbor, three decay rates), CUSUM changepoint statistics, and multi-hop graph-diffusion propagation.

ACLED civilian-targeting aggregatesFree, no registration

Country-month event/fatality counts, an independently-sourced cross-check.

GDELT 2.0 historical signalFree, no registration

A real 2015-2025, 19-country pull (29.7M events, 99.5% of days retrieved), aggregated to country-week tone/volume and joined never-look-ahead. The single largest real gain found before this search phase.

CHIRPS monthly rainfallFree, no registration

Real global rainfall rasters, 2015-2025, windowed-averaged per cell, joined by the prior completed month.

UNHCR asylum-application dataFree, no credentials

Real country-of-origin displacement counts, joined by the prior completed year. 15 of 19 countries returned records.

Not integrated this round

WorldPop population — set aside, disclosed honestly

A real attempt was made to integrate WorldPop gridded population as a structural covariate. It hit real, escalating problems: silently truncated downloads from an over-aggressive timeout (caught via full-file verification, not just byte-count checks), then a resume-incompatible retry that corrupted files further, while true per-country file sizes turned out to be 10-20x larger than initially estimated (Pakistan alone: 544MB). After several hours pursuing this with diminishing returns, it was set aside in favor of the search documented here. Not a dead end — see Tab 05.

Design

Three phases, each answering a different question

Mirrors the parent project's own grand_search discipline: every configuration backtested under real, rolling-origin, never-look-ahead validation, nothing hand-picked after the fact, everything logged.

Phase 1 — Breadth

125 configurations: 25 feature sets × 5 model types

Feature sets spanned individual families in isolation (cell counts alone, GDELT alone, Hawkes alone, etc.), established combinations from earlier rounds, the full "everything" set, and leave-one-family-out ablations. Models spanned XGBoost, Random Forest, Logistic Regression, LightGBM, and the established 3-way ensemble. Used a fast 4-fold rolling-CV (not the full 10-fold) specifically to make 125 real configurations tractable — took 4.1 minutes total. Purpose: map the space broadly before spending expensive compute on rigorous validation.

Phase 2 — Rigor

16 full validations: 8 diverse candidates × 2 horizons, real frozen-threshold discipline

Phase 1's pooled metrics turned out to barely discriminate between configurations (average precision spread of only ~0.02 across all 125) — consistent with this project's repeated finding that pooled cross-validation doesn't differentiate well on this task. So 8 candidates were chosen for genuine diversity (not just top pooled-AP) and re-run under the full 10-fold, frozen-threshold, 80%-precision-target discipline that's actually differentiated configurations throughout this project. Took 4.1 minutes.

Phase 3 — Depth

16 more configurations: real hyperparameter refinement on each horizon's own winner

Phase 2 revealed something phases 1 and offered no reason to expect: no single configuration won both horizons. LightGBM alone was best at 10-day; Random Forest alone was best at 14-day. Phase 3 did a real 8-point hyperparameter grid around each winner specifically (tree depth, learning rate, leaf count, regularization for LightGBM; tree count, depth, leaf size, feature sampling for Random Forest) — and found genuinely better results than phase 2's winners for both horizons. Took 4.4 minutes.

Total

157 real, logged iterations

Every single one backtested with strictly-prior-only training data at every fold; nothing evaluated on data from before the events it's predicting. Full logs: results/grand_search_geolocated_log.jsonl, results/phase2_validation_results.json, results/phase3_refinement_results.json.

The central finding

No configuration wins both horizons — and that's actionable, not just noise

LightGBM alone is the best 10-day model by a real margin (75.7-76.1% vs. 74-75% for every ensemble and RF variant tried) and simultaneously the worst 14-day model tested (67.9%, nearly 8 points behind RF's best). Random Forest shows the opposite pattern less dramatically. This isn't noise — it held up consistently across every ensemble combination tried in phase 2 and was confirmed again in phase 3's hyperparameter sweeps. The practical implication is direct: deploy different models per horizon rather than a single fixed architecture, and treat "which model wins" as a property of the specific question being asked, not of the feature set.

Model choice vs. feature engineering

This phase's gains came from a different lever than rounds 3-4's did

Rounds 3-4 found real but modest gains (roughly 1-3 points) from adding new feature sources (GDELT, CHIRPS, UNHCR) and near-zero or negative gains from re-engineering existing signal (Hawkes kernels, CUSUM, graph diffusion, multi-task modeling). This phase found a comparably sized or larger gain (2-4 points) purely from model type and hyperparameter selection, holding the feature set fixed. Combined, this suggests the two levers are genuinely different and roughly comparably valuable at this point: new data sources helped by giving the model new information; better model/hyperparameter selection helped by extracting more from the information already available. Neither alone was sufficient to reach 80%; both together got closer than any single lever tried in isolation.

Confirmed again

Feature-family gains mostly don't stack

"Everything" (all feature families combined) scored within a point of "round3+GDELT alone" at both horizons (74.1% vs 74.0% at 10-day; 69.6% vs 71.2% at 14-day — the full combination was actually slightly worse at 14-day than GDELT alone). This reproduces round 4's finding at larger scale: once GDELT's signal is present, CHIRPS, UNHCR, Hawkes/CUSUM, and graph diffusion add little beyond it, and can even net out negative by adding noise a fixed-capacity ensemble has to sort through.

Consistent theme

Pooled cross-validation is the wrong tool for choosing among these configurations

Phase 1's 125 configurations spanned an AP range of only 0.49-0.51 — visually and statistically indistinguishable. Yet phase 2's frozen-threshold test on a subset of those same configurations showed real, meaningful, reproducible spreads (67.9% to 75.7% precision). Any future search on this task should treat pooled rolling-CV as a cheap breadth-first filter only, never as the basis for a final decision — a lesson this project has now confirmed at three different scales (round 3's feature tests, round 4's GDELT test, and this 125-configuration search).

Prioritized

What would most plausibly push further

  1. 1

    Deploy the horizon-specific winners as the new production configuration

    Tuned LightGBM for 10-day, tuned Random Forest (depth 10) for 14-day. Free, already validated, no new data or infrastructure needed — purely a configuration change from the single-model-for-both-horizons approach used through round 4.

  2. 2

    Extend the two-stage severity architecture with these new winning configurations

    Round 3's severity fix used the (weaker) 3-way ensemble on the (weaker) round-3 feature set. Rerunning it with the mega feature set and the horizon-specific tuned models is a direct, low-risk next test — severity recall (0.1%-3.9% in the last validated result) is still the most underdeveloped part of this whole task.

  3. 3

    Try LightGBM specifically for severity, given its 10-day occurrence strength

    LightGBM's edge was sharpest at the shorter horizon; severity prediction (a rarer, harder-to-separate label) might benefit from the same model family, untested so far.

  4. 4

    Retry WorldPop population with a proper resumable, chunked downloader

    Set aside this round after real infrastructure problems, not because the underlying idea is weak — it remains a structurally different signal type from everything tested here, which this analysis's own findings suggest is the more promising kind of lever (new information) versus further model tuning (which is likely closer to its ceiling after this phase's sweep).

  5. 5

    A proper stacking meta-learner instead of simple averaging

    Every ensemble in this project has used unweighted probability averaging. Given how differently LightGBM and RF behave by horizon, a learned combination (logistic regression over the base models' out-of-fold predictions) could plausibly capture more than a flat average — untested across all 157 iterations here.

  6. 6

    Push the support-filtering threshold further

    Every result in this search reproduces the ≈2x recall gain from filtering to well-supported cells at no precision cost. Testing higher thresholds (50, 100 historical events) on the new best configurations could trade a modest coverage reduction for a further precision/recall improvement, not yet explored at this scale.
