A proposed fix that didn't work, reported plainly

Mean-fill imputation was the wrong hypothesis

Round 7 proposed mean-fill as a cheap bridge until the WorldPop download finished, reasoning that a more "realistic" default value would beat zero. It didn't: mean-fill underperforms zero-fill at both horizons, and underperforms not using WorldPop at all, at 10-day specifically, by a wider margin than round 7's zero-fill did. The likely reason is structural, not incidental: population is a highly right-skewed quantity (a few dense cities dominate the mean), so filling missing rows with the covered-cell mean (523,079) assigns most uncovered, likely-rural cells an implausibly high value — actively misleading rather than neutral. Zero, for all its own problems, at least sits at the low end of the real distribution. This closes the imputation-engineering angle on WorldPop for now; the honest state of this feature remains "real signal, confirmed in round 7's clean subset test, still blocked on finishing the actual download."

Most promising, confirmed

Severity has a real, usable operating point — at 14-day only

Six rounds of severity results have all inherited the occurrence task's 80% precision target by convention, producing technically-impressive-but-useless precision figures (87-100%) at recall so low (0.3-1.5%) that the model would essentially never flag a severe event in practice. Recalibrating to a 60% target at 14-day breaks that pattern for the first time: 40.3% precision at 11.6% recall is a real, deployable operating point — enough to actually surface severe events to an analyst at a plausible false-alarm rate, rather than a headline number that never fires. This is the most actionable, generalizable finding of this round: severity's operating point should be chosen for what's actually useful, not inherited from the occurrence task by default — and it should be evaluated per horizon, since 10-day's threshold selection does not behave the same way (see below).

Open question, not resolved this round

Why does 10-day severity's threshold selection behave discontinuously?

14-day's target-precision sweep is smooth and monotonic; 10-day's is not (50% and 60% targets both produced actual precision below their target, then 70% jumped straight to the same 93.3% seen at 80%). Given 10-day severity has only 2,395 real positive holdout labels (severity is rarer at the shorter horizon, since fewer 10-day windows accumulate enough fatalities to cross the severity bar) versus 3,151 at 14-day, the most likely explanation is that the select-window threshold search becomes unstable with fewer real severe examples to rank against at low target-precision cutoffs — but this round did not diagnose it directly, and it's flagged honestly as unresolved rather than papered over.

A robustness check that came back reassuring

The support-filter lever is real, not a one-window artifact

This is the first time in eight rounds that a headline lever has been stress-tested against multiple holdout windows instead of the single 60% split used everywhere else. The result is good news for the project's methodology: even though the exact precision varies by 6-7 points depending on which period is held out, it is never below roughly 78-80% at either horizon, across five different split points now tested. The standard 60% split this project has reported throughout turns out to be on the conservative end, not the favorable end, of that range — real evidence against the specific concern that round 6-8's headline numbers were a favorable-window artifact.

What to try next

  1. 1

    Deploy the 60%-target severity model at 14-day alongside the occurrence models

    40.3%/11.6% is a real, usable production candidate for the first time across six rounds of severity work. Free, already validated, no new data or infrastructure — a configuration decision.

  2. 2

    Diagnose 10-day severity's threshold instability directly

    Plot the actual select-window precision-vs-threshold curve around the 50-70% target region rather than only sampling three points — with only 2,395 real positive holdout labels, a few real events shifting between folds could plausibly explain the jump from round 6-8's snapshots alone.

  3. 3

    Close the WorldPop imputation-engineering angle; only full download completion remains open

    Both fills tried (zero, mean) at full-population scale have now been tested and neither cleanly recovers round 7's clean-subset finding that the signal is real. Any future round revisiting WorldPop should either finish the real download (explicitly out of scope again unless directed otherwise) or drop the feature rather than trying a third imputation variant.

  4. 4

    Report the support-filter lever with an honest range, not a single number

    Given the real 6-7 point spread across split points, future writeups should present "≥100 support: 78-86% precision depending on holdout window" rather than a single point estimate — a small honesty upgrade suggested directly by this round's own robustness check.

  5. 5

    Check whether population is already redundant with existing UCDP-history features

    WorldPop's confirmed-real but hard-to-operationalize signal raises the question of why: a direct correlation check between worldpop_population and the existing cell/spatial history features, on the 254 now-covered cells, would clarify whether population mostly duplicates information the model already has from event history, or contributes something genuinely orthogonal.
