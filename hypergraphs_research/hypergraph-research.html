What a hypergraph actually is, why it's a genuinely better fit than a pairwise graph for the specific things that make conflicts spread (shared actors, shared regions, shared shocks, shared named conflicts), a ranked comparison of the free Python tools available, and a real empirical test — new hyperedge types, an alternate propagation operator, a hypergraph-as-features approach via the real xgi library, and a genuine text hypergraph over GDELT's theme taxonomy — run against the project's existing small, large, and pure conflict datasets.

Verdict

Is it promising? Yes on two of three tracks — and the reason why is legible, not a black box

Track B (large, self-scraped, 19 countries, 3 years) is where hypergraphs earn their keep most clearly. It's also the track where the argument for hypergraphs is strongest on paper: 19 countries sharing real cross-border actors and real regional/global shocks in a genuinely time-indexed panel — exactly the multi-way structure a pairwise graph has to approximate with a clique expansion. The data backs the theory here, not just the other way around.
But the ablation (Tab 05) overturns the simplest version of that theory: on Track B, the actor-sharing hyperedge — the single clearest case for a hyperedge in principle — actively hurts (AP 0.270 → 0.179), while the same edge type sharply helps Track C (0.554 → 0.666). The real lesson isn't "hyperedges work" or "hyperedges don't" — it's that a hyperedge is only as good as the entity-resolution quality of the field it's built from, and GDELT's actor codes are noisier than UCDP's hand-curated combatant identities.
Track A (the original 6-country, 180-day panel) shows hypergraph wins too, but nearly every result on that track has fewer than 20 pooled test predictions with 2-3 positives — real numbers, but too small to trust as more than a promising signal. Track C (pure UCDP) is the one place a plain GBM ensemble still beats the hypergraph net outright, worth taking at face value rather than explaining away.

See Tab 05 for the full metric tables (accuracy, precision, recall, specificity, F1, Brier, AP, ROC-AUC, log-loss, MCC) behind every number above, and exactly which new construction — a hyperedge type, a propagation operator, or a feature-engineering shortcut — drove each result. Three configs (Track B/C structural features, Track B text hypergraph) were queued but deferred this session under real CPU contention from a much larger concurrent run — disclosed there, not glossed over.

Recommendation

For this project's actual scale, the free tool worth adopting is XGI — not the deep-learning-oriented libraries

At thousands of nodes, on CPU, with project-specific hyperedge types (shared actor, shared named conflict) that no off-the-shelf loader understands out of the box, a lightweight structural-analysis library that hands off real hypergraph statistics into the project's existing, well-tested GBM pipeline is a better fit than standing up a second, heavier, PyTorch-based training stack for marginal gain at this data size. Definition

A graph connects pairs. A hypergraph connects any-sized groups, in one relation.

An ordinary graph edge always joins exactly two nodes. A hyperedge joins any number of nodes at once — it's a subset of the node set, not a pair. Formally, a hypergraph is a pair (V, E) where V is a set of nodes and E is a set of hyperedges, each hyperedge e ⊆ V. The whole structure is captured by an incidence matrix H (nodes × hyperedges), where H[v, e] = 1 if node v belongs to hyperedge e.

Why this matters for real data

A pairwise graph can only say "A relates to B." To represent "A, B, and C all share the same underlying cause" it has to draw three separate edges (A-B, B-C, A-C) — a clique expansion — which loses the fact that it was ONE shared cause, not three independent pairwise relationships, and which gets denser (and noisier) the more nodes share that cause.
A hypergraph represents that same situation as one hyperedge {A, B, C}. The shared-cause structure is preserved exactly, not approximated.

Why conflict data specifically

The things that actually make conflict spread are multi-way, not pairwise

This isn't an abstract argument — every hyperedge type this project uses corresponds to a real, named relationship in the raw event data that a country-pair or actor-pair graph cannot express as a single relation:

Shared country history

Every week of a given country's own recent trajectory is bound together — this week's escalation risk depends on the whole recent run, not just last week in isolation. One hyperedge per country connects all its recent weeks at once.

Regional and global shocks

A commodity-price spike, a seasonal drought, or a coordinated regional response hits many countries in the same week — one real-world cause, N affected country-weeks. One hyperedge per (region, week) or per calendar week captures this directly; a pairwise graph would need a country-country edge for every pair of countries hit by the same shock, inflating edge count with no new information.

Shared armed actors

A named actor (a GDELT Actor1/Actor2 code, or a UCDP side_a/side_b identity) can be active in multiple countries in the same week — an actor operating across a border links those countries' risk directly. This is the single clearest case for a hyperedge over a pairwise edge: the actor IS the hyperedge, and pairwise-decomposing it (actor active in A and B → draw an A-B edge) throws away which specific actor caused the link.

New this round: shared named conflicts

UCDP's own conflict_name field (e.g., "Government of Sudan – SPLM/A") identifies a specific, real, named conflict that can itself span multiple countries and persist — or go quiet — over specific weeks, independent of which individual armed actor is doing the fighting that week. This is a genuinely different multi-way relation from the actor hyperedge above, built for the first time in this round (see Tab 04).

This isn't a new argument for this project either. model-battery-results.html, from an earlier round, explicitly flagged that every graph-feature attempt up to that point was "genuinely pairwise... flattened to summary statistics fed into a tabular model" and that "none of these five models actually traverse the graph yet." The hypergraph net was built specifically as the answer to that gap — this research round tests whether refining how the hypergraph is built pushes that answer further.
Broader grounding

This isn't a niche technique — it's an active research area, including for exactly this kind of data

  • Hypergraph neural networks as a field started with Feng et al. (AAAI 2019) and Bai, Zhang & Torr's "Hypergraph Convolution and Hypergraph Attention" (Pattern Recognition, 2021) — both implemented and compared in this round (Tab 04/05).
  • Knowledge hypergraphs — recent NLP work (e.g., Text2NKG, NeurIPS 2024) argues that n-ary facts (events involving 3+ entities at once) are better modeled as hyperedges than decomposed into binary knowledge-graph triples, for the same reason argued above for country-weeks: decomposition loses which entities were jointly involved in one real event.
  • Hypergraphs of text — a real, published technique (see Tab 04) models each document as a hyperedge connecting the words or tags it contains, rather than building a pairwise word-cooccurrence graph. This round applies exactly that idea to GDELT's own GKG theme taxonomy (Tab 04/05, "text hypergraph").
  • Conflict forecasting with graph neural networks is itself an active academic literature (spatio-temporal GCNs for subnational violence prediction, dynamic graph contrastive learning for event prediction) — this project's hypergraph work sits inside that broader trend, one step further (multi-way instead of pairwise relations).

New this round

Five genuinely new things tested, none of which repeat the 24 already-logged iterations

1. Hyperedge-type ablation

The production model always builds all four hyperedge types together whenever an actor lookup is supplied — no prior run isolates which one actually carries signal. hg_research_lib.build_incidence_v2 makes each type individually toggleable. Tested cumulatively (country-only → +region_week → +global_week → +actor[→ +conflict for track C]) on all three tracks.

2. New hyperedge type: shared named conflict

UCDP's own conflict_name field, never used as a hyperedge before this round (see Tab 02 for why it's a distinct relation from the actor hyperedge). Built via hg_research_lib.build_conflict_lookup, tested as the 5th ablation step on Track C only (the only track with this field).

3. Alternate propagation operator: Bai et al. 2021 vs Feng et al. 2019

The production model always uses the symmetric Feng et al. operator. hg_research_lib.propagation_operator_v2 adds the asymmetric operator from Bai, Zhang & Torr, "Hypergraph Convolution and Hypergraph Attention" (Pattern Recognition, 2021) — the same formula PyTorch Geometric's HypergraphConv layer implements:

# Feng et al. 2019 (existing, symmetric) G_sym = Dv^-1/2 H W De^-1 H^T Dv^-1/2 # Bai, Zhang & Torr 2021 (new, asymmetric -- PyG's HypergraphConv formula) G_asym = Dv^-1 H W De^-1 H^T

Tested with otherwise-identical hyperparameters on tracks B and C (the two tracks with enough pooled test predictions for the comparison to mean anything).

4. Hypergraph-as-features, via the real xgi library

Every prior hypergraph attempt in this project trains an end-to-end HGNN. This tests the opposite approach: build the identical incidence structure, hand it to the free xgi package (pip-installed for this round, no dependency conflicts with the existing pandas/scikit-learn/xgboost stack — see Tab 06), compute plain structural features per node, and feed those into the project's existing, well-tested GBM pipeline — either alongside the normal tabular features or completely alone (structural signal only, isolating whether hypergraph structure by itself carries any predictive value without any of the usual tabular features). Hyperedge degree and average neighbor degree both made the final feature set; xgi's local clustering coefficient was tried first and dropped after it hung for 60+ seconds on this project's topology — a real finding in its own right, see Tab 05.

5. Text hypergraph: GDELT's theme taxonomy as a genuine multi-way structure

The project's existing text-graph feature (graph_nlp_features.build_theme_embeddings) aggregates articles down to pairwise theme-cooccurrence counts before embedding them (PPMI + truncated SVD — the GloVe/LSA family). That throws away exactly the information a hypergraph is supposed to keep: two articles both mentioning {A, B, C} and one mentioning {A, D, E} produce identical pairwise edge weights for (A,B) and (A,C) either way. theme_hypergraph.py instead treats each country-week as a hyperedge connecting every theme actually tagged in it that week (real membership data already assembled: 813,624 rows), and embeds themes via a TF-IDF-weighted truncated SVD of that real multi-way incidence matrix directly — a genuine "hypergraph of text" construction, not a pairwise collapse. Compared head-to-head against the existing pairwise embedding and against no text features at all, same folds, same base model, Track B.

The single most surprising result: actor-sharing hyperedges — theoretically the clearest case for a hyperedge over a pairwise edge (Tab 02) — sharply hurt Track B (0.270 → 0.179, worse than country-only) while sharply helping Track C (0.554 → 0.666). The honest read: GDELT's Actor1/Actor2 codes on Track B are noisier and more genericly-coded (state/institutional actors reused across huge numbers of unrelated events) than UCDP's side_a/side_b identities, which are hand-curated, specific combatant names. A hyperedge is only as good as the entity-resolution behind it — "shared actor" only helps when the actor field is actually a clean, specific identity, which is a real, transferable lesson for using this construction on other event datasets.
The new conflict-identity hyperedge (Tab 04, item 2) gives Track C its best result in this entire ablation (AP 0.685) — matching the previous 24-iteration sweep's best (0.688, reached only via a hidden-dim hyperparameter search) using a fixed hidden_dim=16 and no hyperparameter tuning at all. The gain here came entirely from a better hyperedge, not a better-tuned network — a genuinely different, complementary lever from the hyperparameter sweeps this project already ran extensively.
Track A's small-N caveat isn't hedging — the numbers show it directly: recall is stuck at exactly 0.100 (1 of the ~10 positives caught) across three of the four configs, meaning most of the AP movement here is one or two individual predictions changing rank, not a real behavioral difference. Directionally useful, not something to act on alone.

On the one track this completed for, hypergraph structure captured as two plain numbers (degree, average neighbor degree) and handed to an ordinary GBM reaches AP 0.186 completely alone — meaningfully above this track's ~0.158 base rate (19/120), with no tabular features at all. Real tooling finding, not a project bug: xgi's nodes.local_clustering_coefficient was tried first and hangs — confirmed via isolated profiling to exceed 60 seconds on just Track A's 160-node, 1,388-hyperedge panel, well before any CPU contention entered the picture. The cause is real: many small, overlapping actor-sharing hyperedges (one per distinct actor code, most spanning only 2-3 country-weeks) push whatever pairwise-overlap computation that metric does into a combinatorial blow-up. degree and average_neighbor_degree, computed on the identical hypergraph, both finished in well under a second. Worth knowing before leaning on xgi's fuller statistics module on a hypergraph built this way — see Tab 06.
Disclosed and not backfilled with invented numbers: Track B and C's structural-feature runs, and the Track B text-hypergraph comparison (Tab 04, item 5), were still queued when this machine's other concurrent job — the user's own 1,150-iteration grand_search_v2 run plus a real local-LLM (icl_ollama_track.py) track — started visibly slowing down under the combined CPU load (its own iteration rate dropped from ~0.61/s to ~0.37/s across this session). The actual recommendation

XGI now, DHG later if the data ever outgrows CPU-scale

1

XGI, for structural-feature engineering into the existing GBM pipeline

Confirmed hands-on this round (Tab 04/05): installs cleanly with zero dependency conflicts, builds the identical incidence structure this project already constructs, and computes real degree/clustering/centrality statistics in under a second even on the largest track. It slots into the project's existing pandas-and-xgboost-centric harness with almost no new surface area to maintain, which matters more here than raw model capacity at a few thousand nodes.

2

Keep the from-scratch HGNN for end-to-end training

It already works, it's fully understood and auditable (no library black box), and — per this round's ablation and propagation-operator results (Tab 05) — the marginal construction choices matter more than the training framework. Rebuilding it on top of DHG mainly buys attention mechanisms and more layer variants, not a fundamentally different result at this scale.

3

Revisit DHG if the panel ever reaches GPU scale

If Track B-style scraping is extended to, say, 100+ countries and multi-year article-level (not aggregated) hyperedges, node/hyperedge counts could reach the range where a proper GPU-backed library with attention and more HGNN variants (DHG, purpose-built by the original HGNN authors) starts to earn its dependency weight. Not there yet.

Next steps

Concrete, free, safe ideas worth trying next

  1. Finish the 3 queued-but-deferred configs first: Track B and C's xgi-structural-feature runs, and Track B's text-hypergraph comparison. All three are coded and ready (hypergraphs_research/run_remaining3.py) — they were deferred mid-session specifically to stop competing for CPU with a larger, higher-priority concurrent run (Tab 05), not because of any unresolved bug. Rerun once that job frees up the machine.
  2. Article-level hyperedges, not country-week aggregates. The current text hypergraph (Tab 04) already improves on the pairwise approach by using real multi-way membership, but it's still aggregated to (country, week, theme, count) — the per-article theme set itself was never persisted (only aggregated on the fly during the original GKG download to save disk). Re-scraping with per-article theme lists kept would let a hyperedge be a single real article, the finest-grained and truest version of "hypergraph of text" for this data.
  3. Attention-weighted hyperedges. Every hyperedge here is uniformly weighted.
