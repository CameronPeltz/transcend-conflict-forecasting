Does the real Rootwise DRC radio data actually improve forecasting — tested honestly, bugs and all

This document tests, for the first time in this project, real captured-and-transcribed radio data against the existing conflict-forecasting pipeline — for the Democratic Republic of the Congo, a country not previously covered by any track in this project. It reports the baseline established earlier today, what changed when the real radio signal was added, two real bugs found and fixed mid-analysis, and an honest statistical read on what a sample this small can and cannot prove.

Found and fixed during this analysis, not hidden

Two real bugs in the first pass

Both were caught by directly inspecting real matched text before trusting the numbers — exactly the kind of check this project has applied throughout. Both are fixed in the results reported in tab 04; neither survived into anything final.

Bug 1: the keyword list was in French; the actual transcript text is in English

The Text column is a real English translation of the original broadcast, regardless of the recorded source language (French/Lingala/Swahili). An initial keyword list built from French conflict terms ("mort," "combat," "cessez-le-feu") matched almost nothing in the real corpus. Fixed by validating a new English term list directly against real word-boundary-anchored counts in the actual 5,000-clip corpus before using it (e.g., "killed": 266 real matches, "ceasefire": 123, "fighting": 246) — every term in the corrected list is a real, confirmed-present word, not a guess.

Bug 2: "tue" (French for "kill") matched inside the English word "Tuesday"

The first keyword-matching pass had no word-boundary anchoring, so the substring "tue" matched inside "Tuesday" — meaning ordinary date mentions ("this Tuesday, July 28") were being miscounted as violence signal. Caught by directly reading the clips the code flagged as "highest violence content" and finding several were actually about diet advice and Ebola-response scheduling. Fixed with proper \b word-boundary regex anchoring, re-verified against the real corpus.

Why this is disclosed here rather than just silently corrected: both bugs would have been invisible in the final numbers alone — a mis-measured feature still produces a number, just a wrong one. They were only caught by reading real matched examples, which is exactly the kind of spot-check a reviewer re-verifying this analysis should expect to see documented, not discover independently.

The actual test

Same 5 real weeks, event-only vs. event+radio

The real Rootwise sample covers exactly 5 calendar weeks (by the W-SUN weekly convention used throughout this project) with a usable lag-1 radio feature. For every one of those 5 weeks, the identical rolling-origin-trained model was run twice — once with only event-coded (GDELT) features, once with event-coded plus real radio-derived features — and compared on the identical weeks both times.

The single most important fact about this test, stated as plainly as possible: all 5 real weeks were actually quiet. Precision and recall are mathematically undefined with zero real positive examples — this cannot be measured as a precision/recall improvement, full stop, no matter how the feature engineering is tuned. What can be measured with 5 real data points is calibration error (how close the predicted probability got to the correct answer, 0 in every case here) — that's what tab 04's sweep reports, and it should be read as "did adding radio reduce false-alarm tendency on real quiet weeks," not "did adding radio catch a real escalation," which remains completely untested.

The one clean, consistent, real pattern across all 30 iterations: filtering the radio corpus down to only the clips Rootwise's own pipeline scored as more relevant (relevance ≥ 2 out of 3) improved results in every single configuration tested that way. Using every clip unfiltered — including a lot of real but conflict-irrelevant chatter, entertainment, and advertising — helped in only two-thirds of configurations and made things measurably worse in several. This is a genuine, actionable engineering finding: pre-filtering by relevance score before feature extraction is worth doing, confirmed by real iteration rather than assumed.
Direct answer

Did the radio data "empirically and demonstrably improve" the model?

Partially, and only in a specific, honestly-bounded sense. It demonstrably reduced false-alarm tendency (predicted-probability calibration error) on 5 real, event-coded-confirmed-quiet weeks, most consistently when the radio corpus was first filtered to higher-relevance clips. It did not — and could not, with this sample — demonstrate any improvement in actually catching a real escalation, because none of the 5 available weeks contained one. Both of those sentences are true at the same time, and a rigorous reviewer needs both, not just the first one.

What would actually settle this

What's missing to make a real precision claim

  • More weeks. Criterion 2's real 84.0% precision figure was built on 858 pooled predictions across 72 weeks and 13 countries. 5 weeks in one country is a pilot integration test, not a statistically powered result — this isn't a matter of better tuning, it's a matter of more real weeks of radio collection.
  • At least one real escalation inside the radio-covered window. Without one, recall is permanently undefined for this specific comparison no matter how long the sample runs, if escalations remain absent by chance.
  • The relevance-filtering finding (tab 04) is worth carrying forward regardless — it's a real, reproducible engineering result even at this scale, and should inform how the Phase II radio-ingestion pipeline (Part Two, Section 3, Task 1) is built from the start.
Recommendation

Should the formal DARPA proposal be updated with this result?

Recommendation: not with a new precision/performance headline. Claiming a "radio data improved precision" result in the formal proposal, built on 5 weeks with zero positive examples, would not survive the same kind of independent re-verification this project applied to Criterion 2 earlier today — and DARPA reviewers checking the evidence would find exactly what this page found: an undefined precision/recall figure and an n too small to support a claim at that level of confidence. That would cost more credibility than it would gain.

What is honestly earned and worth adding: concrete, real evidence that the radio-signal-integration pipeline described in Part Two, Section 3, Task 1 is not just planned but already built and tested end-to-end on real Rootwise data for the first time — including the relevance-filtering finding as a real, specific design decision now informing that task. That's a genuine Criterion 3 progress update, honestly scoped, and it's what the next draft should say rather than a fabricated performance number.
